### 相关项目和模块

## 用户场景与测试

### 用户故事 1：保持可用的模块化导航（P1）

业务用户和技术人员可以通过清晰的工作区导航进入现有页面，刷新或使用前进/后退后仍停留在正确页面，现有一期操作继续可用。

**独立测试**：启动应用后逐个访问文档、任务、知识库、知识类型、标准流程和 Studio 路由，并执行浏览器返回、前进与刷新。

**验收场景**：

1. **Given** 现有数据和 API 可用，**When** 用户通过导航进入任一现有模块，**Then** 页面加载对应数据且 URL 可直接访问。
2. **Given** 用户打开一个详情或多步骤流程，**When** 用户返回来源页面，**Then** 来源路径和必要状态被保留。

### 用户故事 2：专业一致的工作台视觉（P1）

用户在业务区和开发区看到一致、清晰、克制的企业数据工作台，状态、主要操作和信息层级能够快速识别。

**独立测试**：在 375、768、1024 和 1440 像素视口检查核心页面，并使用键盘完成主要导航。

**验收场景**：

1. **Given** 任一核心页面，**When** 页面显示正常、等待、成功或失败状态，**Then** 状态同时通过文字与视觉样式表达且不只依赖颜色。
2. **Given** 键盘用户，**When** 在导航、按钮和表单控件间移动，**Then** 可见焦点与合理顺序始终存在。
3. **Given** 窄屏设备，**When** 打开核心页面，**Then** 页面不产生全局水平滚动且主要操作目标不小于 44px。

### 用户故事 3：开发者可以按模块继续扩展（P1）

开发者可以在明确的 documents、processing、assets 和 indexing 边界内增加页面、API 和服务，而无需继续扩大单一入口文件。

**独立测试**：通过目录和依赖检查确认模块入口可组合，且现有接口测试不需要改变 URL 或响应契约。

**验收场景**：

1. **Given** 模块化壳层完成，**When** 新增某模块页面或路由，**Then** 变更可以局限在该模块和共享契约内。
2. **Given** 现有 API 客户端，**When** 后端切换到模块路由组合，**Then** 原路径和响应继续通过现有测试。

## 范围与影响

### 范围内

- 建立五模块架构命名与导航模型，其中 indexing 和 applications 只作为未来边界。
- 将后端 API 声明拆成可组合的模块路由，同时保持路径和行为。
- 建立前端应用壳、真实路由、布局、模块页面目录和共享 UI 基础。
- 建立 primitive → semantic → component 三层设计 Token。
- 应用新的企业数据工作台视觉风格、响应式和无障碍基础。
- 保持 DataFlow Studio 挂载方式和现有业务流程。

### 范围外

- 新增向量化、向量数据库、图数据库或统一检索。
- 新增 AI 应用运行时。
- 登录、角色、租户和权限。
- 重写 DataFlow WebUI。
- 改变现有业务数据模型或删除兼容 API。
- 为未实现能力增加可操作的空按钮或伪页面。

### 预期项目影响

- **后端**：API 组合方式改变，业务行为与持久化契约保持不变。
- **业务前端**：结构和视觉显著调整，核心操作和 API 契约保持不变。
- **DataFlow Studio**：只调整外围导航/容器，不修改上游工作台业务。

### 跨项目行为

DataForge 继续通过 `DATAFORGE_DATAFLOW_PATH` 或相邻目录发现 DataFlow；Studio 继续挂载到 `/studio`，上游 API 继续使用 `/api/v1`。

## 需求

### 功能需求

- **FR-001**：系统 MUST 在代码和导航模型中表达 documents、processing、assets、indexing、applications 五个一级业务边界。— 来源：SRC-001、SRC-002
- **FR-002**：系统 MUST 将 AI 应用视为 DataForge 外部消费者，并将向量化归入索引与知识服务边界。— 来源：SRC-001、SRC-002
- **FR-003**：后端 MUST 通过模块路由组合提供现有 `/api/*` 接口，不得改变已验证的路径与响应。— 来源：SRC-002、SRC-004
- **FR-004**：现有文档上传、知识任务、知识资产、溯源、标准流程和 Studio 行为 MUST 保持可用。— 来源：SRC-003、SRC-004
- **FR-005**：前端 MUST 使用统一的设计 Token、组件状态、间距、字体和色彩语义，形成专业企业数据工作台风格。— 来源：SRC-002、SRC-005
- **FR-006**：前端 MUST 拆分应用壳、布局、路由、页面模块与共享组件，且核心页面支持响应式、键盘焦点和 reduced-motion。— 来源：SRC-004、SRC-005
- **FR-007**：未实现的 indexing/applications 业务 MUST NOT 显示为可执行功能。— 来源：SRC-003

### 关键实体

- **ModuleDefinition**：一级模块标识、名称、阶段、受众、路由和可用状态的导航契约。
- **DesignToken**：从原始值到语义用途再到组件状态的视觉契约。
- **Workspace**：业务用户或技术人员看到的导航与布局边界。

## 边界情况

- DataFlow 不可用时，业务前端仍可加载，并清晰显示 Studio 不可用状态。
- 直接访问深层前端 URL 时，FastAPI SPA fallback 必须返回应用壳。
- 空数据、加载失败和异步处理中必须有明确反馈与恢复入口。
- 小屏下大型表格或技术数据允许局部滚动，但不能导致页面整体横向溢出。
- reduced-motion 开启时不得运行非必要过渡动画。

## 成功标准

- **SC-001**：现有后端自动化测试全部继续通过，接口路径无回归。
- **SC-002**：DataForge 前端生产构建成功。
- **SC-003**：现有七个页面不再全部定义在单一根组件中。
- **SC-004**：核心页面在 375、768、1024、1440 像素宽度可使用，无全局水平滚动。
- **SC-005**：所有主要可交互控件具有可见焦点，触控目标最小 44px，状态不只依赖颜色。
- **SC-006**：新模块可通过模块注册和路由组合接入，不需要继续扩大原有集中入口。

## 假设

- 继续使用 Vue 3 和 Vite，不迁移 React。
- 继续使用 FastAPI 与 SQLite，不在本次引入微服务或新数据库。
- 用户接受先形成一个可运行的新视觉版本，再对具体页面细节逐模块迭代。

## 依赖

- Vue 3、Vite 和 FastAPI 现有运行环境。
- 现有 DataFlow 和 vendored DataFlow WebUI 集成。
